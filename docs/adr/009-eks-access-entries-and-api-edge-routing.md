# 009 — EKS access entries and API edge routing

## Status

Accepted

## Context

A resumption session, aimed at starting Phase 5 (Observability). Recreating `envs/lab` from scratch (normal ephemerality cycle) got stuck right at the initial `apply`, before any new Phase 5 code — making this entire session about pre-existing bugs from Phases 1 and 4, none of them caught by the functional validation suite so far, because no previous session had exercised `/api/*` end-to-end through CloudFront with a real public request.

## Decisions

### 1. `bootstrap_cluster_creator_admin_permissions = false`

`terraform apply` failed with `409 ResourceInUseException` while creating `aws_eks_access_entry.operator`: when `bootstrap_cluster_creator_admin_permissions = true`, EKS automatically creates a hidden access entry for the identity that calls `CreateCluster`. Since it was `cloudlab-operator` itself (the same identity as `var.operator_role_arn`) who ran the `apply` this time, this automatic access entry collided with the explicit one (`aws_eks_access_entry.operator`, existing since ADR 004 to cover sessions where the cluster is created via CloudShell/root).

This same conflict had already appeared in ADR 007 (item 11) and was resolved there on a one-off basis via `terraform import`. This time the fix is structural: `terraform/envs/lab/eks.tf` turns off `bootstrap_cluster_creator_admin_permissions`. Without it, EKS never creates the automatic access entry — cluster access becomes **100% declared by Terraform**, independent of who runs the `apply`. Confirmed via `get_provider_details` (Terraform MCP) that the argument forces cluster recreation (`# forces replacement`) — not an in-place change, so the fix required destroying and recreating the whole environment in this session (acceptable, since the session had nothing validated yet).

### 2. 30s `time_sleep` before the first `kubernetes_*` resource

Direct consequence of decision 1: `CreateAccessEntry`/`AssociateAccessPolicy` return API success in ~1s, but the EKS control plane's *authorizer* takes a few extra seconds to actually accept the new principal — with no `describe`/wait exposed by the API to confirm propagation. With `bootstrap_cluster_creator_admin_permissions = true`, this never showed up by accident: the creator's permission was born together with `CreateCluster` itself (~10 minutes, plenty of time to propagate). With access now 100% explicit (decision 1), the race was exposed: `kubernetes_namespace_v1.argocd` failed with `403 Forbidden` even with `depends_on` on both access entry resources (the dependency guarantees **API call** order, not actual propagation).

Fixed with `resource "time_sleep" "operator_access_propagation"` (`terraform/envs/lab/argocd.tf`), `depends_on` on both access entry resources, `create_duration = "30s"`, and every subsequent `kubernetes_*`/`helm_release` resource chained to it (via the existing reference to `kubernetes_namespace_v1.argocd.metadata[0].name`).

### 3. API routes under `/api` — an application-side decision, not an edge one

`cloudfront.tf`'s `ordered_cache_behavior { path_pattern = "/api/*" }` forwards the path to the ALB **without rewriting** — the `aws-load-balancer-controller` doesn't rewrite the path either. The API (`app/api/main.py`) only answered root-level routes (`/healthz`, `/videos`), so every public call to `/api/*` hit a 404, never caught because `validate-cloudfront-dns-tls.sh` uploads via `kubectl port-forward` directly to the Service, never through CloudFront/ALB.

Chose to fix it on the application side (`APIRouter(prefix="/api")`) rather than rewriting the path at the edge (CloudFront Function) — keeps route logic visible and testable in the API's own code, without a hidden rewrite layer in the infra that can only be discovered by reading Terraform. Required: bumping the image to `v0.1.2` (ECR), adjusting the Deployment's `readinessProbe`/`livenessProbe` and the Ingress's `healthcheck-path` annotation (which was also unset — the LBC's default is `GET /`, which the API never answered, leaving the target group `unhealthy` and every request `502`), and updating the paths in the two existing validation scripts.

### 4. CloudFront's origin points to its own Route 53 record, not the ALB's raw DNS

Even with decisions 1-3 fixed, `/api/*` via CloudFront still returned `502` — but hitting the ALB directly (`curl -k`) worked. Cause: CloudFront checks TLS hostname against the `domain_name` configured on the origin; `cloudfront.tf` pointed to `data.aws_lb.app_shared.dns_name` (the raw name generated by AWS), but the certificate the ALB serves is the `*.${var.domain_name}` wildcard (same ACM as the Ingress's `certificate-arn` annotation) — with no SAN for the ALB's raw name. The TLS handshake failed before the HTTP request was even forwarded.

Fixed with `aws_route53_record.alb_origin`, an alias A record at `alb-origin.${var.domain_name}` pointing to the ALB — covered by the same wildcard certificate. `cloudfront.tf`'s `alb-api` origin now points to this record instead of the raw ALB DNS. Discarded alternative: `origin_protocol_policy = "http-only"` (simpler, one line) — rejected for removing TLS on the CloudFront↔ALB segment unnecessarily, when a dedicated DNS record solves it without giving up end-to-end encryption.

### 5. `destroy` procedure reinforces ADR 008's technical debt (item 15) — still not automated

The same problem from ADR 008 (ArgoCD Applications without the `resources-finalizer.argocd.argoproj.io` finalizer, leaving the LBC's ALB/security groups orphaned if `destroy` kills the node group before the controller deletes the resources) repeated in this session. This time the manual procedure used (deleting the `Ingress`es before `terraform destroy`, while the LBC is still up) exposed a new nuance: the `app`/`platform` Applications' automatic `selfHeal` undoes the manual `Ingress` deletion, treating it as *drift* — the ALB never got removed on the first attempt. Fixed by pausing `spec.syncPolicy` (`kubectl patch ... -p '{"spec":{"syncPolicy":null}}'`) on both Applications before deleting the `Ingress`es, only then running `terraform destroy`.

Side effect found: manually deleting the ALB before `destroy` breaks `data "aws_lb" "app_shared"` (read unconditionally in any Terraform operation, including `destroy`) — worked around with the same procedure as ADR 008 item 13 (move `cloudfront.tf` out of the directory + temporarily remove the 2 outputs that depend on it, run the `destroy`, restore the files via `git checkout`).

**Still not fixed in code** — the candidates already recorded in ADR 008 remain valid: (a) adopt the finalizer on the Applications that manage LBC resources (slower but automatic destroy); (b) a pre-destroy script that runs `kubectl delete ingress --all -A` + pauses `syncPolicy` + waits for the ALB to disappear, before any `terraform destroy` touches the node group.

### 6. Third occurrence of the LBC orphan — this time blocking deletion of the `argocd` namespace

Separate session, outside the scope of decisions 1-5 (no new code, pure operational recovery). An initial `terraform apply` failed — as expected and already documented in `cloudfront.tf` itself — on `data.aws_lb.app_shared`, because the ALB didn't exist yet (chicken-and-egg between `helm_release.argocd_apps` and reading the ALB in the same run). The `terraform destroy` triggered afterward got stuck in the same pattern as decision 5 above and items 7-9 of ADR 008: the ALB and the LBC's security groups (`k8s-minitube-*`, `k8s-traffic-minitubelab-*`) survived the already-destroyed node group, blocking with `DependencyViolation` the IGW detach ("has some mapped public address(es)", because of the ALB's ENIs with public IP) and the deletion of the two public subnets.

Recovered manually: `aws elbv2 delete-load-balancer` on the orphaned ALB; the two security groups deleted via `aws ec2 delete-security-group` — one of them only freed up after an `aws ec2 revoke-security-group-ingress` on a rule of the EKS cluster's own security group that referenced it (`elbv2.k8s.aws/targetGroupBinding=shared`).

A second `terraform destroy` then got stuck on a new variant of the same root cause: the `argocd` namespace got stuck in `Terminating` because an `Ingress` and a `TargetGroupBinding` inside it carried LBC finalizers (`group.ingress.k8s.aws/minitube`, `elbv2.k8s.aws/resources`) that only the controller (already dead, no node group) would remove. Unlike ADR 008 item 8 (same class of problem): this time the `kubectl patch` to remove the finalizer itself was blocked by the LBC's `ValidatingWebhookConfiguration`/`MutatingWebhookConfiguration`, still registered on the cluster but with no live endpoint (default `failurePolicy` blocks the call instead of letting it through) — had to delete both webhook configurations before `kubectl patch --type=json -p '[{"op":"remove","path":"/metadata/finalizers"}]'` worked.

**Separate operational error, recorded so it isn't repeated:** while trying to resume the interrupted `destroy`, a `terraform apply -auto-approve` was triggered **without the `-destroy` flag** — by default this command converges toward what's declared in the `.tf` files, meaning it would have **recreated** the already-destroyed IGW/subnets/NAT/cluster. Interrupted in time (still in the `refresh`/plan-calculation phase, no `Creating...` had run yet; confirmed via `describe-*` on AWS that nothing was created). Lesson: after any interrupted or partially failed `destroy`, always generate a fresh `terraform plan -destroy -out=<file>` and apply exactly that plan file (`terraform apply <file>`) — never rerun a generic `apply`/`destroy` without a plan file, even with `-auto-approve`, because in that mode it's the command that decides the direction (create vs. destroy), not the operator.

This is the **3rd occurrence** of the same root cause (ADR 008 items 7-9 → ADR 009 decision 5 → here), now also blocking the ArgoCD namespace, not just the network layer. Remains **unautomated** — the two candidates already recorded (the `resources-finalizer.argocd.argoproj.io` finalizer on the LBC Applications, or a pre-destroy script that pauses `syncPolicy` + deletes the LBC's `Ingress`/webhooks before `terraform destroy` touches the node group) need to be implemented before the next apply→destroy cycle.

## Consequences

- `terraform/envs/lab/eks.tf`: `access_config.bootstrap_cluster_creator_admin_permissions = false`.
- `terraform/envs/lab/argocd.tf`: `resource "time_sleep" "operator_access_propagation"`; `kubernetes_namespace_v1.argocd` now depends on it instead of directly on the access entry resources.
- `terraform/envs/lab/versions.tf`: `hashicorp/time ~> 0.14` provider added.
- `terraform/envs/lab/cloudfront.tf`: `resource "aws_route53_record" "alb_origin"`; the `alb-api` origin points to it instead of `data.aws_lb.app_shared.dns_name`.
- `app/api/main.py`: routes moved to `APIRouter(prefix="/api")`.
- `gitops/app/deployment.yaml`: `readinessProbe`/`livenessProbe` on `/api/healthz`; image `v0.1.2`.
- `gitops/app/ingress.yaml`: `alb.ingress.kubernetes.io/healthcheck-path: /api/healthz` annotation.
- `terraform/envs/lab/scripts/{validate-cloudfront-dns-tls,validate-transcoding}.sh` and the corresponding runbooks: paths updated to `/api/*`.
- `docs/runbooks/access-argocd-ui.md` (new): command to fetch ArgoCD's initial password, regenerated every session.
- PR #14 (`fix/eks-access-entry-and-api-healthcheck`), validated in this session via `-var argocd_gitops_revision=<branch>` (ADR 007 pattern, decision 5) before merging, then reverted to the default (`main`) — the merge itself triggered ArgoCD's self-heal to the fixed state, with no additional `terraform apply`.
- Decision 6: no code change — 100% manual recovery via `aws cli`/`kubectl` against the already-existing infrastructure. Environment confirmed destroyed at the end (EKS cluster, VPC, NAT, ALB, LBC security groups, EIPs — all absent via the AWS API directly). High priority for automating pre-destroy cleanup in the next session.
